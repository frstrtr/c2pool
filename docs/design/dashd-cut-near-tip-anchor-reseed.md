# Near-tip MN-list anchor reseed — design note (operator sign-off required)

Status: DESIGN ONLY. Not implemented. This is a **reward-path** change and must
not ship without operator sign-off, because it moves the trust root of the
masternode-payee queue.

Scope: the daemonless DASH cut only (`--coin-rpc` removed). It is the answer to
one question the operator raised — *can a fresher, fork-tip-predetermined
anchor be trusted so the ~1.5 h anchor→tip cold replay shrinks* — answered
strictly by porting what dash-core actually does, not by loosening a guard.

---

## 1. What dashd actually does (the portability finding)

dashd never trusts a *runtime* near-tip masternode-list snapshot. It **derives**
the deterministic MN/SML list forward, block by block, from an initial empty
snapshot at the DIP-3 activation height:

- `CDeterministicMNManager::BuildNewListFromBlock` runs at every `ConnectBlock`
  (evo/deterministicmns.cpp:660-693), writing a per-block `DB_LIST_DIFF` and a
  full `DB_LIST_SNAPSHOT` every `DISK_SNAPSHOT_PERIOD = 576` blocks
  (deterministicmns.h:681).
- `GetListForBlock` answers a query by walking to the nearest snapshot and
  `ApplyDiff()`-ing forward (deterministicmns.cpp:778-833) — a fold.
- The `getmnlistd(base,target)` / `CSimplifiedMNListDiff` transport
  (simplifiedmns.cpp) is **verified catch-up between two heights**, not a trust
  shortcut: the receiver re-derives and checks the cbTx merkle root
  (`CalcCbTxMerkleRootMNList`, simplifiedmns.cpp:98). There is no
  assumeutxo-for-masternodes and no near-tip SML download that skips derivation.

The **only** release-pinned trust surface dashd carries is a *compiled* one:
`nMinimumChainWork` + `defaultAssumeValid` + `checkpointData`
(chainparams.cpp:221-222, currently height 2487500). Crucially,
`defaultAssumeValid` skips **script-signature** verification only for blocks
below it (validation.cpp:2337-2366) — merkle roots and **all** evo/MN
processing are still fully computed and checked. dashd bumps that compiled
checkpoint to a more-recent height **every release**, delivered as reviewable
software, never as a runtime "adopt newest" decision.

### Consequence for c2pool

c2pool's compiled anchor (mainnet `2513000`) is the exact analog of dashd's
`defaultAssumeValid` + `checkpointData` trusted floor. Both then **derive
forward**, so the served MN-payee / quorum-root / credit-pool bytes come out of
the same deterministic apply and are dashd-exact. The refuse-newer-anchor guard
(`mn_checkpoint_lane.hpp:816-849`) is therefore **matching dashd's semantics**,
not over-conservative: it blocks only a reward-unsafe *runtime* newest-first
reseed-on-divergence; it does **not** block the initial cold anchor selection,
and it does **not** block bumping the compiled checkpoint floor in a release.

**The dashd-correct way to deliver a fresher floor is a release-pinned compiled
anchor bump.** That is the recommendation. Everything below is the minimal,
reward-safe port that makes that mechanism first-class and auditable.

---

## 2. The design: a compiled, release-pinned anchor bump (the reward-safe port)

This is not a runtime trust change. It is the c2pool mirror of dashd bumping
`defaultAssumeValid` each release, plus the guard-rails that make the bump as
safe as dashd's.

### 2.1 What ships in a release

The anchor is already a compiled blob:
`src/impl/dash/coin/checkpoints/dash_mn_checkpoint_mainnet.inc`, regenerated by
`tools/dash/gen_mn_checkpoint.py`. The bump is:

1. Regenerate the checkpoint at a **fresher, deeply-buried** height H_new
   (recommend H_new ≤ tip − `nMinimumChainWork`-equivalent burial, i.e. the same
   depth dashd requires before it will pin a checkpoint — never near the live
   edge). H_new must be at least `COINBASE_MATURITY` + reorg-safety below the
   tip observed at release time.
2. The generated blob carries, as it does today: height, blockhash, the full
   per-masternode payee set, and provenance (`source`, `generated`). It is a
   text artifact a reviewer can diff against a synced dashd's `protx list` at
   H_new (this is the `CheckpointSetIsFieldIdenticalToRpcSeed` KAT shape,
   already in the suite).
3. Operator sign-off = review + merge of the release that carries the new blob.
   This is the sign-off gate. No runtime flag can select a fresher anchor.

### 2.2 Why this is safe — three properties dashd also has

- **Deeply buried.** A checkpoint below the reorg horizon cannot be replaced by
  a competing fork; the chain-position check
  (`mn_checkpoint_lane.hpp:1353-1376`) verifies the anchor hash against the
  node's own PoW-validated header chain before a single block is folded, and
  fails closed on mismatch. This is dashd's `checkpointData` position semantics.
- **Derived, not trusted-forward.** The anchor is a *starting snapshot*; every
  block from H_new→tip is still re-applied and its coinbase payee cross-checked
  (`apply_block` payee-desync fail-closed). The fresher anchor shortens the
  fold; it does not skip any derivation, exactly as a dashd `defaultAssumeValid`
  bump shortens script-verification but not MN derivation.
- **Reviewable.** The bump is a diff in a compiled artifact, byte-checkable
  against a canonical dashd at the same height, gated by human merge — the same
  objectivity dashd relies on for its release checkpoint bumps.

### 2.3 What it buys

The cold replay window collapses from (tip − 2513000) blocks to (tip − H_new)
blocks. Cutting the anchor forward by, e.g., 8000 blocks removes ~8000 folds
from every cold start — the direct lever on the ~1.5 h replay, at zero
reward-safety cost because the derivation that remains is byte-identical.

### 2.4 What must NOT change (the invariant this note protects)

- The refuse-newer-anchor guard (`mn_checkpoint_lane.hpp:816-849`) stays
  **exactly** as-is. It refuses a *runtime* newer/at-or-after-divergence anchor
  on a re-arm. A compiled bump does not go through that path — it arms with
  `m_anchor_height == 0` (initial cold arm), which the guard explicitly permits
  — so nothing here loosens it.
- No `--embedded-mn-anchor-height=<newest>` style runtime override. That would
  be the reward-unsafe "adopt newest at runtime" dashd never does.

## 3. The runtime alternative, and why it is rejected

One could imagine a runtime reseed that fetches an SML at a near-tip height and
arms from it, skipping the fold entirely. This is rejected because it is
precisely the trust shortcut dashd does **not** take:

- A `getmnlistd(base=genesis-empty, target=near-tip)` result is only trustworthy
  *after* the receiver re-derives and checks the cbTx merkle root at target —
  which requires walking the diffs, i.e. the fold we were trying to skip. A
  near-tip SML accepted **without** that re-derivation is an unauthenticated
  "newest state", and on a *repeat* divergence it re-arms a queue that already
  contains the divergence (the exact hazard the guard's comment at
  :826-829 describes) → a coinbase the network rejects.
- There is no DIP that commits a near-tip full MN-list to a single verifiable
  root the way `checkpointData` commits a buried block. So a runtime near-tip
  anchor has strictly *less* authentication than a compiled buried one, for a
  speedup the compiled bump already delivers safely.

If a future DIP adds a consensus-committed near-tip MN-list snapshot (analogous
to assumeutxo's committed UTXO hash), this decision should be revisited: at that
point the receiver could verify a near-tip anchor against an in-band commitment,
and the runtime path would gain the same authentication the compiled path has.
Until then, the compiled bump is the only reward-safe fresher floor.

---

## 4. Recommendation

1. **Adopt the compiled anchor bump as the release ritual.** Add a release-step
   that regenerates `dash_mn_checkpoint_mainnet.inc` at a freshly-buried height,
   diff-verified against a canonical dashd `protx list`, merged under operator
   sign-off. This is the dashd-correct fresher floor and needs no code change to
   the lane or the guard.
2. **Keep the refuse-newer-anchor guard unchanged.** It is dashd-semantic.
3. **Do not add a runtime near-tip anchor override.** Revisit only if a DIP adds
   a consensus-committed near-tip MN-list root.

The throughput belt shipped alongside this note (event-driven body re-request +
bulk/backfill deconfliction) is orthogonal and reward-safe: it speeds the *same*
correct anchor→tip fold without moving the anchor, and needs no sign-off.
